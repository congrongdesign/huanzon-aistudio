# 可编辑 PPT 模块前端页面与模块拆解文档

## 1. 目标

本文档定义 `可编辑PPT` 模块的前端信息架构、页面结构、组件拆分和交互规则。

目标：

1. 新增一个独立模块，不破坏现有画布与 PPT 工作台
2. 支持导入、识别、逐页检查、元素修正、导出
3. 支持后续推送到现有 `PPT 工作台`

---

## 2. 产品定位

`可编辑PPT` 不是风格生成模块，而是识别与重建模块。

它解决的是：

1. 把图片版 PPT 变成尽量可编辑
2. 把 PDF / 图片集转成结构化页面
3. 为后续 AI 美化提供更干净的输入层

所以它应当与：

1. `画布`
2. `PPT 工作台`
3. `批量模块`

并列，而不是嵌到其中任意一个内部。

## 5. 页面区域拆解

## 5.1 顶部工具栏

### 功能

1. 导入文件
2. 任务名
3. 解析状态
4. 配置入口
5. 重新解析
6. 导出
7. 推送到工作台

### 建议按钮

1. `导入`
2. `重新解析当前页`
3. `重新解析失败页`
4. `导出可编辑 PPT`
5. `推送到工作台`

### 状态展示

1. 当前任务状态
2. 总进度
3. 已完成页数 / 总页数
4. 失败页数

---

## 5.2 左侧栏：任务与页面

左侧栏建议分两层：

### 第一层：任务列表

展示：

1. 最近任务
2. 任务状态
3. 页数
4. 创建时间
5. 失败标记

### 第二层：当前任务页面列表

展示：

1. 页码
2. 缩略图
3. 标题
4. 页面角色
5. 解析状态
6. 置信度

### 建议交互

1. 支持只看失败页
2. 支持搜索页码/标题
3. 支持快速跳转到第 N 页

---

## 5.3 中央主区域：页面预览与编辑

中央区域是核心。

建议分成 3 个视图模式：

1. `原稿`
2. `识别预览`
3. `分层预览`

### 原稿视图

显示原始页面图，用于对照。

### 识别预览

在原稿上叠加：

1. 文本框边界
2. 图片框边界
3. 形状框边界
4. 表格区域

### 分层预览

根据 AST 渲染对象层，让用户看到“导出后 PPT 大概长什么样”。

### 中央区交互

1. 点击元素高亮
2. 拖拽调整位置
3. 拖拽缩放框
4. 双击文本直接编辑
5. 右键改元素类型

---

## 6. 页面流程设计

## 6.1 空状态

进入 `可编辑PPT` 模块时，如果没有任务，显示大面积导入区。

空状态内容建议：

1. 标题：`导入原稿，恢复为可编辑PPT`
2. 支持格式说明：`PPTX / PDF / 图片ZIP / 批量图片`
3. 一键上传按钮
4. 最近任务快捷入口

---

## 6.2 导入中状态

上传后进入任务初始化状态。

显示：

1. 当前文件名
2. 拆页进度
3. 当前阶段说明

不要只显示“处理中”，要写清：

1. `正在拆页`
2. `正在识别文字`
3. `正在分析版式`
4. `正在构建对象层`

---

## 6.3 解析完成状态

任务解析完成后，默认进入第一页的 `识别预览`。

页面提示：

1. 成功页数
2. 失败页数
3. 可手动修正
4. 可导出

---

## 6.4 失败页状态

失败页不能只显示报错文字。

建议卡片化展示：

1. 页码
2. 缩略图
3. 失败原因
4. 重新解析按钮
5. 降级导出为图片页按钮

## 8. 状态管理建议

你的项目目前大量使用组件内状态，因此第一版可以继续沿用 `useState + useMemo + useCallback`，不要一开始引入额外状态库。

建议主状态：

```ts
type EditablePptUiState = {
  jobs: EditablePptJob[];
  activeJobId: string | null;
  pages: EditablePptPage[];
  activePageId: string | null;
  elements: EditablePptElement[];
  selectedElementId: string | null;
  viewMode: "original" | "detected" | "layered";
  loading: boolean;
  exporting: boolean;
  filters: {
    status: "all" | "ready" | "failed" | "processing";
    keyword: string;
  };
};
```

### 状态边界建议

1. 主组件持有任务、页面、选中态
2. Canvas 只管渲染和交互事件
3. Inspector 只根据选中元素读写属性

## 9. 交互规则

## 9.1 页面切换

切换页面时：

1. 保存当前页未提交修改
2. 拉取目标页元素
3. 保持当前视图模式不变

## 9.2 元素选中

规则：

1. 单击元素选中
2. Shift 支持多选可后续再加，V1 可先不做
3. Delete 删除或隐藏元素
4. Esc 取消选中

## 9.3 文本编辑

规则：

1. 双击文本进入编辑态
2. Enter 提交
3. Esc 取消

## 9.4 重新解析

支持 3 种粒度：

1. 重新解析当前页
2. 重新解析失败页
3. 整套重跑

## 12. 与现有工作台联动

建议在右上角提供一个按钮：

- `推送到 PPT 工作台`

点击后：

1. 选择目标工作台项目或创建新项目

`先恢复 -> 再美化`

## 14. 推荐开发顺序

最合适的前端落地顺序：

1. 先搭页面框架和空状态
2. 接任务列表与页面列表
3. 接单页预览
4. 接元素详情与编辑
5. 最后接导出和推送工作台

原因：

1. 能尽快看到完整工作流
2. 即使识别算法还没完全稳定，也能先把 UI 骨架跑通

---

## 15. 结论

前端上最重要的不是“做一个复杂编辑器”，而是把流程做清楚：

1. 导入
2. 看结果
3. 修正
4. 导出
5. 推送到后续工作流

因此第一版应该优先：

1. 流程清晰
2. 状态可见
3. 错误可恢复
4. 页面与元素层级足够可理解

只要这 4 点做好，后续算法能力增强后，这个模块就能自然成长。
